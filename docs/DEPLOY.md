# Deploy runbook — Render (app + managed Postgres)

Test deploy runs under **Navreo's** accounts; migrate to QwintiQ's for final handover
(SOW §11). Human steps are marked 🙋; everything else is in the repo. The app
**self-bootstraps its tables** on first boot (`init_db`), so there is no manual schema step.

## 1. Push the repo (automatable)
The code is a private GitHub repo. If not pushed yet:
```
gh repo create qwintiq-vault --private --source . --push
```

## 2. Render — one Blueprint deploy 🙋
1. Render → **New → Blueprint** → pick the `qwintiq-vault` repo. `render.yaml` provisions
   both the web service **and** a managed Postgres (`qwintiq-vault-db`); `DATABASE_URL` is
   injected automatically — nothing to paste.
2. Fill the four `sync:false` env vars when prompted:
   - `ANTHROPIC_API_KEY` — Navreo's key (makes the skills return real work, not the mock)
   - `AI_ARK_API_KEY` — optional; enables the list-building/partner data proxy
   - `ADMIN_EMAIL` / `ADMIN_PASSWORD` — the control-panel login. **Required** — the app
     refuses to boot in prod without them (no default admin ships).
   `SECRET_KEY` is generated by Render; `RENDER=true` (set in the blueprint) turns on the
   fail-closed prod guards.
3. Deploy. First boot runs `init_db` against the managed Postgres and seeds the shared
   icebreaker setup + partner routines.

## 3. Smoke test the live service (automatable — this is also the Postgres path's first run)
```
curl -s -o /dev/null -w "%{http_code}\n" https://<service>.onrender.com/admin/login   # 200
curl -s https://<service>.onrender.com/.well-known/oauth-authorization-server | grep https  # all URLs https
cd tests && python test_gate.py https://<service>.onrender.com                        # 13/13 against real PG
```
(The gate suite creates + removes a throwaway consultant, so it also exercises every
Postgres code path end-to-end. Re-add real consultants afterward.)

## 4. Custom QwintiQ domain (optional, later) 🙋
Render service → Settings → Custom Domains → add `vault.qwintiq.com`; CNAME it to the Render
hostname. TLS is automatic. Until then the `*.onrender.com` URL is fully usable as a
custom connector.

## 5. Onboard a consultant (the handover demo)
1. Control panel → **Add consultant** → **Copy full invite** → send them the one message.
2. They open the welcome page, run the one connect line, sign in with the temp password,
   and set their own password on first sign-in.
3. Cut access any time with **Revoke key** (reversible) or **Remove** (permanent).

## Alternative DB: Supabase
If you'd rather use Supabase than Render Postgres: remove the `databases:` block from
`render.yaml`, set `DATABASE_URL` to the Supabase connection string (`sync:false`), and
(optionally) run `db/schema.sql` in Supabase — though `init_db` will create the tables on
first boot either way. Everything else is identical.

## Alternative host: Docker (Fly.io / Railway) — if Render is unavailable
The repo ships a `Dockerfile` + `fly.toml`, so the identical vault runs on any container host.
Fly.io example:
```
fly launch --no-deploy                 # reads fly.toml (VAULT_ENV=prod turns on prod guards)
fly postgres create && fly postgres attach <db>   # sets DATABASE_URL, or use any external PG
fly secrets set ANTHROPIC_API_KEY=... SECRET_KEY=$(openssl rand -hex 32) \
                ADMIN_EMAIL=... ADMIN_PASSWORD=...     # AI_ARK_API_KEY optional
fly deploy
```
Then smoke-test exactly as in step 3 against the `https://<app>.fly.dev` URL. Railway is the
same idea (Dockerfile auto-detected; set the same env vars; attach a Postgres plugin). Keep it
to **one instance** — the MCP session manager and rate limiter hold in-memory state.
